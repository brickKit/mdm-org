# mdm/org 的设计

本页写这个组件为什么这样设计：术语、拥有的数据、状态与规则、命令与事件、实现状态与未决问题。写给要修改它的人与 AI。怎样使用、部署与配置在 `BRICKKIT.md`；代码在哪、怎样构建与测试在 `AGENTS.md`；跨组件的规则在装配项目的协议 02（投影的来源与水位）、协议 07（生命周期）、协议 14（时间与日历、列表）、协议 15（安全来源的意图证据）与安全 07（组织树维度）。

## 边界

拥有法人与组织：法人的基础资料，每个法人下的部门树与部门路径，部门里的岗位；以后还有汇报关系、地点与工作日历。所有客户都需要它：法人与部门是授权范围、账簿与单号的基础。

| 不在这里 | 归谁 |
| --- | --- |
| 会计期间与关账 | `erp/finance`（D05） |
| 员工、任职、员工与账号的映射 | `mdm/employee` |
| 业务伙伴与它们在法人下的角色 | `mdm/partner` |

## 术语

| 业务叫法 | 定义 | 代码标识符 |
| --- | --- | --- |
| 法人 | 记账与合规的单位：代码、名称与译名、国家、时区、本位币、会计年度起始月 | `legal_entity` |
| 法人的时区 | 明确的 IANA 时区：请求给出，或取部署配置的默认值并写进记录；没有就拒绝，不取服务器时区或 UTC。法人的业务日期按它计算 | `timezone`、`DEFAULT_LEGAL_ENTITY_TIMEZONE`、`/business-date` |
| 部门 | 法人下的一棵树中的一个节点 | `org_unit` |
| 部门路径 | 法人身份、再从上到下的部门身份，用 `/` 连接；按段比较，是授权的组织树维度（安全 07）。改名不变，只有移动改变 | `path` |
| 路径历史 | 一个部门有过的每条路径与起止时刻；当前的没有结束时刻 | `org_unit_path_history` |
| 岗位 | 一个部门里的一个职位：员工的任职挂在法人、部门、岗位上（`mdm/employee`）；审批按“部门内持有该岗位的人”找处理人（协议 09）。岗位只属于一个部门，不挪动：换部门是退役旧岗位、新建岗位（任职随之结束与新建，安全 04 的“有安全含义的变化”） | `org_position` |

## 拥有的数据

| 表 | 内容 | 终态与保留 |
| --- | --- | --- |
| `legal_entity` | 法人；代码全局唯一 | `retired` 不可恢复；不删除 |
| `org_unit` | 部门：法人、上级、代码（法人内唯一）、名称、路径（唯一）、状态 | `retired`；不删除 |
| `org_unit_path_history` | 每个部门的路径历史 | 永久保留 |
| `org_position` | 岗位：法人、部门、代码（法人内唯一）、名称与译名、状态 | `retired` 不可恢复；不删除 |

以后还有：汇报关系、地点、工作日历（按法人与地点的变体）及其版本。

每条法人与部门的记录带版本，每次变化在同一个事务里以完整状态事件发布。子树按路径前缀查（`text_pattern_ops` 索引）。法人与组织不进迁移：安装或上线时经本组件建立（协议 16）。

## 状态与规则

法人（协议 07 的生命周期）：

| 当前状态 | 命令 | 结果 |
| --- | --- | --- |
| `active` | 暂停 | `suspended` |
| `suspended` | 恢复 | `active` |
| `active`、`suspended` | 退役 | `retired`（不可恢复） |

部门只有 `active` 与 `retired`，退役不可恢复（没有恢复的命令；要用就新建部门）。不变量：

- 法人建立时有明确的时区与本位币（协议 14）。
- 部门树无环；树的每次结构变化（新建、移动、退役）先锁法人的行，串行执行，两个并发的移动拼不出环。
- 移动时，本部门与下面全部部门的路径在同一个事务里更新，每个都有新版本、事件与路径历史。
- 下面还有启用部门的部门不能退役；部门里还有启用岗位的也不能退役（先退役岗位）。
- 岗位只有 `active` 与 `retired`，退役不可恢复；新建岗位要法人与部门都启用，和部门的结构变化一样先锁法人的行（与部门退役串行）；岗位不移动，只改名与译名。
- 路径按段比较：子树是“前缀加 `/`”，`a/b` 不是 `a/bc` 的上级；没有部门的主体不贡献部门条件，空路径不是根（安全 07）。

**安全来源**：本组件是组织树的**水位来源**（协议 02）。收紧性的组织调整先在事务外写意图证据，再提交（协议 15，3.0.16 起，`internal/tightening`）：
- 记什么：部门退役；部门移出它原来的某个上级（移动后原来上级链里有一个不再是上级）；法人暂停或退役；岗位退役（持有人随之失去按岗位的资格，3.0.34 起）。类别都是 `org_tightening`，`change.kind` 分别是 `retirement`、`move_out`、`legal_entity_status`；对象是部门（`mdm.org.unit`）、法人（`mdm.org.legal_entity`）或岗位（`mdm.org.position`），带变更前的版本。
- 不记：新建、改名、只往下挪（上级链只增不减）、法人恢复为启用；这些不收紧任何人的范围，恢复时丢了也只会少给。
- 怎样写：意图按不加锁先读到的记录写；在树的锁下办完后，确实收紧了才在同一个事务里写结论（变更历史与提交序号），被拒、没变化、只是放宽的写“已取消”。移动是否收紧要在锁下才知道（新上级可能同时被挪动），所以启用部门的每次移动都先写意图。
- 缩小范围：本组件现在没有这种调整（岗位、地点等随后续加入时再按这条规则补）。

其余：发件行在锁内按提交后编号，发布位置带纪元，事件只含可投影字段；高可用部署中全部写入同步提交（D66）。

## 命令与查询

| 命令或查询 | 用户面或系统面 | 权限键 |
| --- | --- | --- |
| 新建与修改法人；法人的状态 | 用户面 | `mdm.legal_entity.manage` |
| 读取与列出法人；法人的业务日期（`/business-date`） | 用户面 | `mdm.legal_entity.read` |
| 新建、改名、移动、退役部门；部门的上级（自上而下）、路径历史、按法人或上级列出 | 用户面 | `mdm.org_unit.manage`（读取 `mdm.org_unit.read`） |
| 新建、改名、退役岗位；按法人、部门或状态列出岗位 | 用户面 | `mdm.org_position.manage`（读取 `mdm.org_position.read`） |
| 来源方法 `Snapshot`、`Read`（聚合是法人、部门与岗位，一次最多 500 个） | 系统面 | `mdm.org.system.read` |
| 水位来源的补取 `CatchUp` | 系统面 | 本版答“能力不支持” |

## 事件

流 `mdm.org`（4 个分区）：`mdm.legal_entity.changed.v1`、`mdm.org_unit.changed.v1`、`mdm.org_position.changed.v1`（3.0.34 起），都是完整状态。以后加汇报关系的状态事件、工作日历的版本、水位回声（作为授权与资格判断的来源，协议 02）。移动一个部门时，下面的每个部门各自发事件；消费者按记录的版本应用，不需要理解“子树”。

## 依赖

不调用任何组件。身份、授权（必需）；`infra/audit`（可选，兼任证据存储：缺时收紧的意图走外部告警渠道，协议 15）。

## 数据范围

本版没有维度。部门路径是别的组件的数据范围维度；本组件自己的读取是否按法人限定，列入未决问题。

## 未决问题

- 工作日历的模型（按法人与地点的变体、版本；审批截止按创建时的版本，协议 09）。
- 按生效日期的组织变更怎样与路径历史、授权的生效点对齐。
- 水位回声与补取（协议 02 的来源水位）的实现。
- 部门与岗位退役时不检查谁还在引用它（员工的任职、授予里的部门路径）：已有的授予按路径继续匹配；退役是否要先清理或转移这些引用，随 `mdm/employee` 与授权一起定。本组件不读员工（主数据不读下游），员工组件消费岗位的退役事件，结束挂在它上面的任职。
